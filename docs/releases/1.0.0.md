# Axoloty 1.0.0 release notes

> These notes record the 1.0.0 release content for the `axoloty/1` CBOR
> profile. The repository `VERSION` advances to `1.0.0` in the release commit;
> until then, `main` is pre-1.0 and `VERSION` reads `0.9.0`.

Axoloty 1.0.0 adds the `axoloty/1` CBOR wire profile and makes it the only
Zenoh encoding, while `coaty/3` JSON stays sealed on MQTT. It also sets the
1.0 API freeze. The full list of changes is in
[`CHANGELOG.md`](../../CHANGELOG.md).

## `axoloty/1` CBOR

The `axoloty/1` profile carries the Coaty Core Profile 3 event families and
object semantics unchanged over a deterministic CBOR payload (RFC 8949
§4.2.1). It uses a separate route prefix, `axoloty/1`, so a receiver selects
the profile from the route and never from a content-type hint. The profile
uses text map keys, encodes a UUID as tag 37 over a 16-byte byte string, and
allows only tag 1 (epoch time) and tag 37. The reader rejects indefinite
lengths, non-minimal integers, duplicate map keys, and excessive nesting. The
bounds are 256-byte routes, 2,048-byte payloads, and 32 levels of nesting. See
[`docs/protocol/axoloty-1.md`](../protocol/axoloty-1.md) for the full CDDL,
error model, and the CBOR-only consumer limitations.

`coaty/3` is unchanged. Its field presence and wire bytes are identical to
0.9.0. The `wire-cbor` tier runs the frozen `coaty/3`/`axoloty/1` golden corpus
and the host/static trace-parity replay on every pull request.

## Zenoh carries only `axoloty/1`

Zenoh now carries only the `axoloty/1` CBOR profile
([ADR 0009](../adr/0009-zenoh-carries-only-axoloty-1.md)). The binding
publishes every profile payload with the `application/cbor` encoding and drops
a profile sample labelled with any other encoding. MQTT keeps the sealed
`coaty/3` JSON profile. See
[`docs/transports/zenoh.md`](../transports/zenoh.md).

### Migration: 0.9.x Zenoh peers do not interoperate

A Zenoh peer built on 0.9.x carried the `coaty/3` JSON routes. A 1.0 Zenoh
peer carries only `axoloty/1` CBOR. The two do not interoperate, and there is
no runtime negotiation or dual mode. Upgrade both peers to 1.0. MQTT peers are
unaffected.

## Embedded consumers

[`docs/embedded-consumer-contract.json`](../embedded-consumer-contract.json)
declares both wire profiles. `axoloty1CBOR` is mandatory and does not require
`_JSONCore`; `coaty3JSON` requires it. A CBOR-only contract omits `jsonCore`,
and `AxolotyWire` builds without `_JSONCore` with `--disable-default-traits`.
Three known limitations remain: the borrowed `BorrowedMessage` entry points are
JSON-gated, `axoloty-tool embedded consumer prepare` still requires
`_JSONCore`, and the trace-replay seed helper is JSON-only. They are recorded
in
[`docs/protocol/axoloty-1.md`](../protocol/axoloty-1.md#cbor-only-consumers).

## Tooling

The inspector and MCP decode `axoloty/1` payloads with a bounded CBOR value
model and diagnostic notation. `make checkpoint` continues to build every
public product in debug and release.

## Known limitations

- A CBOR-only `axoloty-tool embedded consumer prepare` path is a tracked
  follow-up under
  [#977](https://github.com/phynics/axoloty/issues/977).
- The `ProtocolTraceRuntimeReplay` seed helper is JSON-only. It is test
  support, not production code.
- Device performance budgets remain from the C surrogate and do not match
  production Embedded Swift measurements
  ([#987](https://github.com/phynics/axoloty/issues/987)).
- macOS and iOS are declared platforms without automated CI.
