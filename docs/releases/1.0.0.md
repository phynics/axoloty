# Axoloty 1.0.0 release notes

Axoloty 1.0.0 is the first stable release. It freezes the six Core products
(`Axoloty`, `AxolotyWire`, `AxolotyProtocol`, `AxolotyObjectModel`,
`AxolotyStaticRuntime`, and `AxolotyMQTT`) under the
[versioning and deprecation policy](../versioning.md). It adds no public API
over 0.10.0: the reviewed public-symbol baseline,
[`docs/api/core-1.0-public-symbols.json`](../api/core-1.0-public-symbols.json),
is unchanged since that release. The full list of changes is in
[`CHANGELOG.md`](../../CHANGELOG.md), and source changes made during the API
audit are in [the migration note](../migration/pre-1.0-to-1.0.md).

The owner decided to cut 1.0 on 2026-11-01
([#1059](https://github.com/phynics/axoloty/issues/1059)).

## What 1.0 promises

- The six Core products follow Semantic Versioning. A minor release adds
  backward-compatible API and may deprecate; a patch release contains only
  backward-compatible fixes; removal needs a major release.
- `coaty/3` stays sealed. New behavior uses a separately versioned profile.
- Everything else is experimental and may change in any release: `AxolotyZenoh`
  and `AxolotyZenohCore`, `AxolotyCoatyModels`, `AxolotyIoRouting`,
  `AxolotySensorThings*`, the `Tools/` harness, and the products in
  `phynics/axoloty-debug`.

Support levels do not widen at 1.0, as
[`docs/SUPPORT_MATRIX.md`](../SUPPORT_MATRIX.md) records. Linux is validated
and macOS is best effort. iOS is experimental and unvalidated. MQTT with the
`coaty/3` JSON profile is validated against the CoatyJS reference agent pinned
at 2.4.0. Zenoh and the `axoloty/1` CBOR profile over it are experimental.
The `axoloty/1` wire format is frozen: a breaking change needs a new profile
identifier. The Zenoh transport and the device path around it stay
experimental, so their behavior and support level can still change.

## `axoloty/1` CBOR

The `axoloty/1` profile carries the Coaty Core Profile 3 event families and
object semantics unchanged over a deterministic CBOR payload (RFC 8949
§4.2.1). It uses a separate route prefix, `axoloty/1`, so a receiver selects
the profile from the route and never from a content-type hint. The profile
uses text map keys, encodes a UUID as tag 37 over a 16-byte byte string, and
allows only tag 1 (epoch time) and tag 37. The reader rejects indefinite
lengths, non-minimal integers, duplicate map keys, and excessive nesting. The
bounds are 256-byte routes, 2,048-byte payloads, and 32 levels of nesting. See
[`docs/protocol/axoloty-1.md`](../protocol/axoloty-1.md) for the full CDDL and
error model. The profile first shipped in 0.10.0.

`coaty/3` is unchanged. Its field presence and wire bytes are identical to
0.9.0. The `wire-cbor` tier runs the frozen `coaty/3`/`axoloty/1` golden corpus
and the host/static trace-parity replay on every pull request.

## Zenoh carries only `axoloty/1`

Zenoh carries only the `axoloty/1` CBOR profile
([ADR 0009](../adr/0009-zenoh-carries-only-axoloty-1.md)). The binding
publishes every profile payload with the `application/cbor` encoding and admits
every sample by its validated route. A non-CBOR label never gates delivery.
The binding does not count a diverging label; earlier documents said it did
([#1062](https://github.com/phynics/axoloty/issues/1062)). MQTT keeps the sealed
`coaty/3` JSON profile. The Zenoh package stays experimental and separate from
the six root products. Its evidence is on Linux x86_64 and macOS arm64
([`docs/dependencies/zenoh.md`](../dependencies/zenoh.md)), which does not make
macOS a validated platform. See
[`docs/transports/zenoh.md`](../transports/zenoh.md).

### Migration: 0.9.x Zenoh peers do not interoperate

A Zenoh peer built on 0.9.x carried the `coaty/3` JSON routes. A Zenoh peer on
0.10.0 or 1.0.0 carries only `axoloty/1` CBOR. The two do not interoperate, and
there is no runtime negotiation or dual mode. Upgrade both peers. MQTT peers
are unaffected.

## CBOR-only portable consumers

[`docs/embedded-consumer-contract.json`](../embedded-consumer-contract.json)
declares both wire profiles. `axoloty1CBOR` is mandatory and does not require
`_JSONCore`; `coaty3JSON` requires it. `embedded consumer prepare --profile
axoloty1CBOR` selects all five portable modules without `_JSONCore`.

Since 0.10.0 the CBOR-only surface is proven by behavior
([#1063](https://github.com/phynics/axoloty/issues/1063)). Advertise, Discover,
Resolve, Deadvertise, Channel, Update, and Complete run through the static
runtime, with exact payload bytes, Discover/Resolve and Update/Complete
correlation, and wrong-correlation rejection. These are tested absences, with
no CBOR equivalent: predicates, filters (`ObjectPredicate`,
`CoatyFilterAdapter`), and the JSON-only object-model APIs (`ObjectEnvelope`
decoding and `ObjectFieldDecoder`). The Core gate probes each absence at
compile time.

In a build without `_JSONCore`, JSON decoding paths that remain callable now
return typed failures instead of trapping. See
[`docs/protocol/axoloty-1.md`](../protocol/axoloty-1.md#cbor-only-consumers)
and [the consumer contract](../embedded-consumer-contract.md#wire-profiles).

The hardware-free gate compiles and partially links the CBOR-only graph for
RISC-V. It also compiles that graph in Embedded Swift mode for the host,
executes the full Core consumer fixture there, and checks both artifacts for
`_JSONCore` symbols. It does not execute anything on RISC-V or on a device.

## Device evidence

Embedded profiles `esp32c6-zenoh` and `esp32c6-mqtt` are certified in
[`phynics/axoloty-embedded`](https://github.com/phynics/axoloty-embedded) at
`0.10.0-embedded.2` on Core v0.10.0, a pre-release tag. No device certificate
names Core 1.0.0. Embedded will relock to 1.0.0 and requalify both profiles
afterwards under
[phynics/axoloty-embedded#73](https://github.com/phynics/axoloty-embedded/issues/73),
so 1.0 ships before its device certificates exist. The `sensor-node` reference
profiles keep their evidence and budgets and are not certified. This
repository did not re-verify the embedded certificates and holds no hardware
evidence.

## Tooling

The inspector, MCP server, and `serve mqtt|mcp|dev` live in
[`phynics/axoloty-debug`](https://github.com/phynics/axoloty-debug), pinned to
0.10.x until it re-pins to 1.0
([phynics/axoloty-debug#6](https://github.com/phynics/axoloty-debug/issues/6)).
`make checkpoint` continues to build every public product in debug and release.

## Dependencies

The `brace-expansion` update in the CoatyJS reference agent lockfile clears
three Dependabot alerts. The package is used only by the wire-compatibility
test harness and is not part of any shipped product.

## Known limitations

- The performance budget manifest is still `provisional`. Host latency and
  binary-size budgets await a second clean run
  ([#303](https://github.com/phynics/axoloty/issues/303)), and device budgets
  are not final. See [`docs/performance-budgets.md`](../performance-budgets.md).
- macOS has no automated CI, and iOS is declared but unvalidated.
- Kept out of 1.0: [#1061](https://github.com/phynics/axoloty/issues/1061)
  (`StaticRuntime.receive` stack cost),
  [#1060](https://github.com/phynics/axoloty/issues/1060) (soft-state
  presence for Zenoh),
  [#1044](https://github.com/phynics/axoloty/issues/1044) (observable-object
  workflows), and [#998](https://github.com/phynics/axoloty/issues/998) (macOS
  validation).
