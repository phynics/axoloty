# Axoloty 1.0.1 release notes

Axoloty 1.0.1 is a patch release of the frozen Core 1.0 products. It changes no
wire bytes and no public declaration: the reviewed public-symbol baseline,
[`docs/api/core-1.0-public-symbols.json`](../api/core-1.0-public-symbols.json),
is unchanged. The full list of changes is in
[`CHANGELOG.md`](../../CHANGELOG.md).

## What changed

A runtime that connected after a peer advertised never learned that the peer
was gone, including from the broker last will. `ProtocolProcessor` rejected an
inbound Deadvertise unless its object table already held a matching entry, and a
late joiner has no entry for a peer that advertised before it connected
([#1067](https://github.com/phynics/axoloty/issues/1067)).

An inbound, well-formed Deadvertise is now delivered whether or not it matches
anything in the table
([#1068](https://github.com/phynics/axoloty/pull/1068),
[#1071](https://github.com/phynics/axoloty/pull/1071)). This matches pinned
CoatyJS 2.4.0, which keeps no object table and delivers any Deadvertise whose
`objectIds` is an array of non-empty strings (`src/com/deadvertise.ts` and
`src/model/types.ts` at commit 4a77168). Both wire profiles, `coaty/3` and
`axoloty/1`, share the one processor, so both get the fix, on host and static
runtimes alike.

Well-formed means `objectIds` is an array of non-empty strings:

- Delivered: an empty array, identifiers the runtime has never seen, and strings
  that are not UUIDs.
- Rejected: a missing `objectIds`, a value that is not an array, an empty
  string, and an element that is not a string.

A local Deadvertise stays strict. It must be an array of UUIDs that names at
least one announced local object.

## Who is affected

Consumers that join a network after their peers advertised, and that observe
the `deadvertise` event stream to track peer departure. They now see the peer's
deadvertisement, including the last will published on an unclean disconnect.
Consumers that were present when the peer advertised see no change for a
Deadvertise that matches.

Consumers now also see Deadvertise events for identifiers they never knew.
Do not assume a delivered payload names a known object, or that each name is a
UUID.

## Behavior to know

- A Deadvertise that matches nothing creates and removes no state. A payload
  removes only the entries its own source owns, whatever it names.
- A repeated Deadvertise is delivered each time. The processor does not
  de-duplicate it, so a handler may see the same departure more than once.
- Each accepted delivery increments the processor generation, as every accepted
  input does, but creates no state.

## Test harness

The live wire scripts under `Tests/Support/WireCompatibility` could print `PASS`
after a failed Swift test, because `podman wait` exits 0 whatever the container
status ([#1070](https://github.com/phynics/axoloty/issues/1070)). They now fail
on a nonzero container status
([#1072](https://github.com/phynics/axoloty/pull/1072),
[#1073](https://github.com/phynics/axoloty/pull/1073)). All live scenarios were
rerun with the real exit status and passed. This changes no shipped code.

## Compatibility and support

No wire bytes change, `coaty/3` stays sealed, and the support levels in
[`docs/SUPPORT_MATRIX.md`](../SUPPORT_MATRIX.md) do not widen.

Device certificates are not on this release. `esp32c6-zenoh` and `esp32c6-mqtt`
are certified in `phynics/axoloty-embedded` at `0.10.0-embedded.2` on Core
v0.10.0. No certificate names Core 1.0.0 or 1.0.1, because embedded relocks and
requalifies under
[phynics/axoloty-embedded#73](https://github.com/phynics/axoloty-embedded/issues/73).
This repository did not re-verify those certificates.
