# Axoloty 0.8.1 release notes

Axoloty 0.8.1 is a tooling and packaging fix release with no public API
change. It is the revision `phynics/axoloty-embedded` locks against, tracked
by [epic #845](https://github.com/phynics/axoloty/issues/845). It remains a
pre-1.0 release.

Consumers already on 0.8.0 who do not build the portable packages on an Apple
host need no changes.

## macOS is a supported preparation host

Preparing Core for a firmware build on macOS did not work in 0.8.0. Two
independent defects caused it, and both are fixed.

The five standalone portable packages declared no `platforms`, so SwiftPM
defaulted them to macOS 12 on an Apple host while their sources use
`InlineArray`, which requires the 26.0 SDKs. Building any of them natively
failed with `'InlineArray' is only available in macOS 26.0 or newer`, and
`axoloty-tool embedded consumer prepare` failed with it too, because it builds
the standalone `AxolotyStaticRuntime` package. They now declare the same
26.0 macOS and iOS floor the root package has declared since 0.6. Linux and
Embedded Swift targets resolve no Apple platform version, so the firmware,
container, and CI paths are unchanged.

Preparation then looked for the macro executable under exactly the contract's
spelling, which ends in `-tool`. That is SwiftPM's native build system naming.
Swift Build, the default on an Apple host from Swift 6.4, emits the bare
target name, so preparation reported that the macro executable had to be
inside caller-owned scratch when it already was, under a different name.
Preparation now tries the contract spelling first and falls back to the
unsuffixed name.

The contract document and `docs/embedded-consumer-contract.json` are unchanged,
and the preparation report still carries the resolved absolute path, so a
consumer that reads the report needs no name handling of its own.

Linux through the pinned container remains the reference host and the one
required CI uses. A macOS host prepares Core but cannot run the firmware
build, which needs ESP-IDF.

## Packaging correction

`Packages/AxolotyWire/Package.resolved` was committed by accident in
[#880](https://github.com/phynics/axoloty/pull/880) and is removed. It was a
host build byproduct, and it pinned swift-nio 2.103.0 and swift-system 1.8.1
where every other standalone portable package pins 2.101.3 and 1.7.5, so a
consumer of the standalone wire package could have resolved a different
closure than the rest of the portable set.

## Validation

Required CI passed on each change. On macOS 26 with Swift 6.4, the five
standalone portable packages build natively, and
`axoloty-tool embedded consumer prepare` completes and reports schema 1,
status `prepared`, the five portable packages in dependency order, `_JSONCore`
at the locked revision, and the resolved macro executable. The same
preparation was driven end to end from an external firmware checkout through
its own bootstrap script.

The riscv32 Embedded consumer gate, the firmware build, and device evidence
are unchanged from 0.8.0 and were not re-run on hardware for this release. No
portable production source changed.

